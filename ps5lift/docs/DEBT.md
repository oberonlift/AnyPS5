# Known gaps

## Bugs

A review of the whole tree in October 2026 found these. Each gives a wrong result, corrupts state or reports a misleading error instead of stopping cleanly. None is fixed yet, and most have no fixture that would catch them.

### Lifter

- A divide error (a zero divisor or a quotient wider than the operand) stops the program with its address, as `ud2` and `int3` do; a guest exception handler does not see it.

### x87

- Unnormals, pseudo-NaNs and pseudo-infinities are computed as SoftFloat normalises them, instead of raising IE and returning the indefinite; `fxam` already classifies them as unsupported.

### Discovery and images

- [Discovery](../lifter/src/Discovery.cpp) decides whether an address a RIP-relative `lea` takes is a function by how the code after it uses it. That lets data through: a string or table in an executable segment whose address is passed to a call, stored or spilled is decoded as code, which stops the lift or adds bogus call targets. A target inside a known function splits it, which can cut a guarded jump table off from its jump. An error in a start found this way does not name the `lea`. Checking the target itself (that it lies between known functions and decodes cleanly to a terminator) would replace the use patterns.
- `TableBound` accepts a `cmp`/`ja` guard reached through its taken edge, where the index is above the bound; walks past calls that clobber a caller-saved index, which `ReachingDefinitions` does not; and takes `sub idx, K; ja` as a bound on the result, which wraps. Each gives a table that is marked guarded but too short, whose missing cases stop in `ps5lift_dispatch`. A guarded table whose entries run past readable data is also cut short there without an error.
- The linear sweep keeps only data references outside executable segments, so a reference into a table that shares a segment with code does not end the table before it.
- `CalledImport` recognises a PLT stub only when its first instruction is the `jmp`, so a call to `setjmp` through an IBT stub (`endbr64; bnd jmp`) gets no resume point; the fixtures build with `-fcf-protection=none`. Its stub probe decodes outside `DecodeReached`, so an undecodable call target fails without naming the call.
- [GuestImage](../lifter/src/GuestImage.cpp)'s filter for the CIE personality drops LSDA landing pads outside their FDE, such as those a compiler moves into a cold section, which then are not resume points.

### Runtime

- Resuming a suspended fiber on a thread other than the one that started it stops with `resuming a lifted fiber on another thread not implemented`. Each lifted and bridge frame on the fiber's stack holds the `Ps5LiftState` it was entered with, so the fiber would run on the first thread's state while that thread runs on it too; [GuestCpu](../runtime/src/GuestCpu.cpp) only restores the fiber's registers into the current thread's state. Fiber job systems resume a fiber on whichever worker thread is free, so titles with one stop here. A fiber's entry, a callback thunk, never returns, so the native thread that starts one counts a callback still running and keeps the guest's floating-point environment for its own code from then on. A state for each fiber, which the switch makes current, would fix both.

## Gaps

- [Discovery](../lifter/src/Discovery.cpp) seeds functions from the entry point, `DT_INIT`, the function exports, the `.symtab` function symbols, `.eh_frame`, relocation targets in executable segments and the addresses code takes with a RIP-relative `lea` (see the bugs above), then follows direct calls. It reads the init and fini arrays only through their relocations. A function only reached through a pointer that none of these finds stops at run time in `ps5lift_dispatch`.
- [Jump tables](../lifter/src/Discovery.cpp) whose guard is not recognised, such as one that compares a stack slot and loads the index from another, are sized by the data references around them. A reference into the table ends it early, which stops at run time in `ps5lift_dispatch` when a missing case runs; data that nothing refers to after the table, with words that happen to point into the function, adds entries, and one that lands inside an instruction stops the lift.
- [GuestImage](../lifter/src/GuestImage.cpp) applies `R_X86_64_64`, `GLOB_DAT`, `JUMP_SLOT` and `RELATIVE` at lift time, at the executable's link addresses and at the base `ps5lift` gives each module; `R_X86_64_DTPMOD64`, `DTPOFF64` and `TPOFF64` against the image's own symbols, and packed relative relocations (`DT_RELR`); any other relocation type, including copy relocations and TLS relocations against another image's symbols, stops the lift, as do a relocation against an IFUNC and a dynamic table without its size tag. IFUNC resolvers are not run. An unresolved weak undefined symbol becomes an import like any other, so a guest whose weak reference no AnyPS5 library bridges fails to link rather than reading 0. An image's references to its own symbols are not interposed by an earlier image's, as `ld.so` would interpose them without `DT_SYMBOLIC`. PS5 inputs have to be relinked first; `ps5lift` does not read SELF or SCE dynamic tables itself.
- A `call` or `jmp` through an import slot is lifted as a direct call to the import, which is wrong if guest code rewrites that slot.
- A lifted program loads only the guest modules it was lifted with, those its executable needs through `$ORIGIN`. AnyPS5's `dlopen`, and so `sceKernelLoadStartModule`, finds one by file name, in any case as AnyPS5's file lookup does, with or without the relinker's `.guest.prx` suffix, so two modules of one name in different directories are not told apart; it runs the module's lifecycle table on the first load. Any other name goes to the host's loader, which loads AnyPS5's system libraries, and `dlsym` on one of those returns a host address that guest code cannot call. `dlopen(NULL)` and the default scope search the lifted images' exports only, not AnyPS5's libraries.
- [The runtime](../runtime/src/Runtime.cpp) maps the whole image read-write (through AnyPS5's guest arena when its libc is linked in), and runs modules' initializers but not the executable's nor any finalizer; the relinker's entry stub is the only entry contract tested.
- [The lifter](../lifter/src/Lifter.cpp) supports integer, BMI1/BMI2, atomic and string instructions, SSE/AVX2 integer and floating-point instructions, FMA3 and F16C. These are reported as unsupported and stop at run time: gathers, `maskmovdqu` and `maskmovq`, `rcl` and `rcr`, `pushf` and `popf`, `xlat`, `enter`, `psign`, `mpsadbw`, `movnti`, `movntpd`, `movq2dq`, `movdq2q`, the conversions between MMX and SSE registers (`cvtpi2ps`, `cvtps2pi` and the rest), `vzeroall`, `xsave` and `xrstor`, the x87 instructions listed below, `syscall`, `bt`, `bts`, `btr` and `btc` with a register bit offset and a 32-bit address, far `call`, `jmp` and `ret`, a 16-bit `leave`, and `fnstenv` and `fldenv` with the 14-byte 16-bit environment. So are SSE4a's `extrq` and `insertq` with the field in a register or past bit 63; their immediate forms keep the destination's upper quadword, which AMD leaves undefined, and were checked against the APM's definition only, since no AMD machine is at hand. AES-NI and `pclmulqdq` lift on 128-bit registers only: VAES and VPCLMULQDQ on 256-bit registers are AVX-512-era extensions the reported Zen 2 lacks, and code that checks `cpuid` does not reach them. `shld` and `shrd` with 16-bit operands, whose counts above 16 give undefined results, and 16-bit `bswap`, which is undefined, stop as well.
- [`cpuid` and `xgetbv`](../runtime/src/Cpuid.cpp) answer as an AMD Zen 2: with the signature of AMD's 4700S desktop kit, which is built on the PS5's chip (family 17h, model 47h, stepping 0), and with the user-mode extensions LLVM enables for `znver2` plus the optional ones AnyPS5's host check lists for the console. None of it is measured on a console. The highest leaves reported are 0xd and 0x80000001, so code reads the cache, topology and brand-string leaves as absent; leaves 5 and 6 and `xgetbv` of a register other than XCR0 stop the program.
- An unaligned ordered load or store is a plain access with a fence. x86 makes an unaligned access within a cache line single-copy atomic; aarch64 makes a plain one atomic only within 16 bytes with FEAT_LSE2, and not at all without it. Locked instructions, `xchg`, `xadd` and `cmpxchg` still declare their natural alignment, so an unaligned one, a split lock on x86, faults. Vector loads and stores wider than 64 bits are not ordered.
- Lifted calls nest on the host stack, which the runtime sizes at 512 MiB for every guest thread, those libkernel starts included; a native thread that calls guest code has the host stack its creator gave it. `longjmp` unwinds lifted frames ([Jump.cpp](../runtime/src/Jump.cpp)), but not native frames between them: a `longjmp` out of a guest callback that native code called stops the program. Guest C++ exceptions work when their personality routine is AnyPS5's (`__gxx_personality_v0` or `__gcc_personality_v0` imported by name or NID); a personality routine in guest code is not called, unless the title's own unwinder calls it. A `ret` on a switched stack resumes only in a frame on the current host stack, at one of its resume points, so a guest context switch to another stack (a coroutine) stops the program, and one that leaves by an indirect `jmp` rather than a `ret` is not followed. A helper that assigns RSP and returns on a shifted stack, rather than adjusting it with `add` or `sub`, would be read as a switch. A fiber's guest entry point is stored as its callback thunk, so `sceFiberGetInfo` reports the thunk's address rather than the guest's. The target frame of a `longjmp` is the innermost one with a `setjmp` call whose entry stack pointer is at or above the saved one, which assumes the frame did not move its stack pointer above that value after `setjmp`.
- The status flags are not kept in the state: only DF crosses calls, returns and dispatch, or all of them with `--preserve-flags`. `pushf` and `popf` are not lifted.
- Under qemu 8.2.2 the lifted vector fixture built for `neoverse-v2` at -O0 (relaxed) and -O3 (TSO) crashes with SIGSEGV on a store to mapped, writable memory, and the same binary prints the expected output with `-one-insn-per-tb`; builds for `neoverse-n1` and every x86-64 build pass. The same `neoverse-v2` builds, SVE included, pass natively on the GB10 (`run_fixture.py --cpu neoverse-v2`), so this is a qemu translation bug. The test driver runs aarch64 code under qemu with `-one-insn-per-tb` to avoid it.
- [FMA](../lifter/src/Lifter.cpp) NaN priority (left multiplicand, right multiplicand, addend) was measured on an Intel Xeon; Zen 2 is unverified.
- Which NaN `dpps` and `dppd` return when two or more products are NaN or infinite differs between x86 implementations: an Intel Goldmont Plus and a Coffee Lake add the products in different orders, neither the SDM's, and Zen 2 is unmeasured. The lifter follows the SDM's pseudocode, and the `sse41` fixture hashes such a result as one canonical NaN.
- `rcpps`, `rcpss`, `rsqrtps` and `rsqrtss` return the correctly rounded `1/x` and `1/sqrt(x)`, not Zen 2's approximations.
- `stmxcsr` reports the exception flags the host FPU raised; an operation that `--float exact` computes with integer code, such as `vcvtps2ph` with an immediate rounding mode, raises none.
- FTZ without DAZ, or DAZ without FTZ, is exact only on aarch64 CPUs with FEAT_AFP; elsewhere either bit flushes inputs and outputs. The fixtures only exercise both together.
- LLVM assumes the default floating-point environment, so an operation it constant-folds uses round-to-nearest whatever the guest MXCSR says.
- libkernel for a lifted guest: `getcontext`, `setcontext`, `swapcontext` and `sigreturn`, which switch guest stacks, report themselves as not implemented. A `sceKernelRaiseException` handler sees the registers of the target thread's last call, with `rip` its return address, not of the instruction it interrupted, runs on a stack of its own rather than below the interrupted frame, and its changes to the context are dropped. The dynamic linker binds a function that two libraries define to the first library linked, which is only right while both definitions behave the same; exports with C++ linkage, which AnyPS5 also publishes by NID, have no bridge.
- Data imports are told apart from function imports by the symbol's ELF type; an untyped undefined symbol is treated as a function. Copy relocations and TLS imports are not supported. AnyPS5's libc exports no type_info for fundamental types (`_ZTIi` and so on), so a guest that throws or catches one fails to link.
- [The bridge generator](../tools/generate_bridges.py) skips exports that return complex values or take a function pointer as a callback's argument, and leaves `setjmp` and `longjmp`, which need the guest's own registers, to the runtime; it bridges only `extern "C"` exports. It passes and returns a record by value when it is plain old data without a base class, bit-fields, a packed layout or a function pointer, and skips it otherwise, although native code can call a guest function pointer it finds in a record (see the design's callbacks), since one in a returned record would reach guest code as a host address; a callback cannot take or return one. A variadic export calls its `v` sibling, which takes a `VaList*`, when it has one; one without forwards the remaining integer registers when its variable arguments start in a register, and is skipped otherwise. libc gets 1532 bridges and 27 exports have none. [check_record_bridges.py](../tools/check_record_bridges.py) compares the classification of 15 record shapes with clang's own x86-64 lowering and compiles their copied layouts for both hosts, but only records returned in integer registers run in a fixture (`div` and its siblings); the runtime's paths for record parameters, SSE eightbytes and records in memory have not run. libkernel's variadic `open`, `fcntl` and `sem_open` read their optional argument with the host `va_arg` and have no `v` sibling yet.
- Native calls through a guest function pointer read from memory pass only the arguments and results the host keeps in registers, cost a signal each, and the x86-64 host's trampoline has not run. [Callbacks](../runtime/include/ps5lift/Bridge.hpp) take and return scalars only, and each signature has 256 thunks; the 257th distinct guest address for one signature stops the program. The guest state a foreign native thread gets on its first callback lives until that thread exits.
- [GuestCpu](../runtime/src/GuestCpu.cpp), the guest FPU state that a lifted AnyPS5 libc reads: x87 is only its control and status words, so `fegetenv` reports every x87 register empty; `fwait` with an unmasked pending x87 exception ends the program where the console raises SIGFPE; the MXCSR support mask is reported as `0xffff`, not measured on a PS5. Flags that lifted arithmetic raises reach `fetestexcept` through the host FPU, but LLVM may reorder or fold floating-point operations around a call because it assumes the default environment.
- AnyPS5 libc in lifted mode: all 68 sources compile for aarch64 and x86-64, and seven of upstream's libc test programs pass on both (`tools/run_libc_tests.py`). The rest of upstream's tests are not run yet. `GuestStdioVariadic`'s `_Vacopy` check reads the copy with the host `va_arg`, so lifted builds skip it. C++ exceptions thrown and caught by the libc itself use the host's unwinder in lifted builds; guest exceptions, which AnyPS5's own unwinder handles on x86 hosts, are not supported. A host caller's `long double` variadic argument is rounded to 80 bits before formatting.
- [x87](../runtime/src/X87.cpp): the transcendental instructions (`fsin`, `fcos`, `fsincos`, `fptan`, `fpatan`, `f2xm1`, `fyl2x`, `fyl2xp1`), `fxtract`, `fbld`, `fbstp`, `fsave`, `frstor`, `fnop` and `ffreep` are reported as unsupported. `fprem` always finishes the reduction in one step, so C2 is never set, and the C bits of an `fprem` with a NaN result and the rest of the x87 behaviour were measured on an Intel Xeon, not on Zen 2. An unmasked x87 exception ends the program at the next `fwait`, not at the next x87 instruction, and `fnstenv`, `fxsave` and `fxsave64` record zero instruction and operand pointers and last opcode. `fxsave` writes the first 416 bytes of its area and leaves the reserved rest alone; the `fx-state` fixture matched an Intel Pentium Silver (Goldmont Plus) for the words, MXCSR and its mask, the loaded registers and an XMM register.
- [Guest long double](../3rdparty/anyps5/core/libs/prx/libc/include/GuestLongDouble.hpp): on aarch64 the libc's `long double` code computes in binary128 and rounds once to 80 bits, while the console rounds every x87 step to 64 bits, so a function of several operations can differ in its last bit, and round-to-nearest can round twice. When both operands of a host operation are NaNs, the host, not x87, picks which one comes back. The precision control in the x87 control word does not apply to host code. `long double` callbacks, `long double` complex results (`__mulxc3`, `__divxc3`) and the locale's `putLongDouble` member are not bridged. Host binary128 arithmetic on aarch64 is itself in software (libgcc), so a SoftFloat-backed guest type would cost about the same and remove these differences.

## Tests

- Every fixture is built for `znver2`, so the compiler encodes SSE with VEX, and the only legacy SSE forms tested are AES, `pclmulqdq`, SHA, MMX and a set of scalar arithmetic, comparison, rounding and conversion forms, which come from assembly. `vector.c` and `float.c` use AVX throughout, so covering the packed legacy forms needs SSE-only builds of their tests.
- No test runs `--float fast`, `--preserve-flags` or `--emit-ir`, and no fixture splits an image into more than one part, so calls between the parts of one image are tested only by EVO Player.
- Untested paths: division traps, jump tables sized by layout, the generator's forwarded variadics and 128-bit stack arguments, and the runtime's reports of a guest `int`, a full callback pool, a `longjmp` through native code and a resume a frame has no point for.
- The TSO check in `threads.c` can only fail when the lifted code runs on aarch64 hardware.

## Cleanup

- [Lifter.cpp](../lifter/src/Lifter.cpp) is about 3150 lines, most of them one class. `EmitSemantics` falls back to trying five `Emit*` functions in turn, so which one owns a mnemonic is not stated anywhere, and instruction families are split across them: `shufps` and the immediate `vpermilps` are vector kinds while `shufpd` and `vpermilpd` are in `EmitFloat`, and the broadcasts are lifted from two places. `EmitVector` derives each kind's operand shape from lists of kinds. One table from mnemonic to handler would also be the place to check prefixes and branch types.
- Switches pick an operation for values they do not name instead of failing: `SignExtendAccumulator`, `BitScan`, `VectorBitwise`, `BitManipulation`, `Shift` and `ShiftDouble` in the lifter, `EmitVector`'s `default`, which reports a lifter bug as an unsupported guest instruction and hides `-Wswitch`, and the x87 runtime's `Arithmetic` and `CompareConditions`. `ps5lift_string_op` treats every operation other than 0 as `stos`; its enum exists only in the lifter, and the x87 constant indexes and comparison codes are bare numbers on both sides.
- Target selection is spread over `main.cpp` (the default CPU, by triple prefix), `Codegen.cpp` (the required features) and `Lifter.cpp` (the triple check), and the lifted module has no data layout until code generation.
- Duplicated: the in-lane masks of the integer and floating-point horizontal operations; the EFLAGS mapping of `fcomi` and `comiss`; the x87 runtime's 80-bit reads and writes and its rounding table, and its wait check, which `GuestCpuX87Wait` reimplements with its own exit; `Hex` in three files; the lift, link and run steps of the four fixture runners; the NID header in `run_libc_fixture.py`.
- Dead: `ImplicitGpr`, `LowElements`, `AtomicRmw`'s `default`, `VZEROALL` in `FindUsedRegisters`, `Fpu::Operand`, `CalledImport`'s branch for a direct call to an import, the export of `ReturnsTwice` from its header, `emit`'s `library_name` parameter, the bodies in `libc_native.c`, the LLVM components the lifter links but does not use, and `ps5lift_thread_create` and `ps5lift_thread_join`, which only `host_bridge.cpp` uses.
- `GuestImage` is complete only after `PlaceTls` and `Relocate`; until then its imports and code pointers are empty, and nothing stops a caller from reading them. `Read` handles six concerns in one function.
- `pshufb` and `vpermd` are lifted as one variable-index extract per element, which aarch64 lowers through the stack; `tbl` does the same in one instruction.
